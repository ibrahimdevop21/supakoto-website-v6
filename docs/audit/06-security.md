*Read-only audit. Branch: feat/phase-23-forms-destination. Live: https://supakoto.com. 2026-08-25.*

## Details per finding

**#1 — No security headers.** `next.config.ts` defines `redirects()` and `outputFileTracingIncludes` but no `headers()` function; there is no `vercel.json` to fill the gap. Live responses for `/`, `/en/booking`, and the 404 page all carry only Vercel's platform defaults (`strict-transport-security`, `x-vercel-*`) — nothing app-defined. Fix: add a `headers()` block in `next.config.ts` (or `middleware.ts`) setting at minimum `Content-Security-Policy` (start with a `script-src` allow-list for `www.googletagmanager.com`, `connect.facebook.net`, `analytics.tiktok.com`, `www.google-analytics.com`, plus `'self'`; note inline scripts from `next/og`/RSC hydration may need a nonce or `'unsafe-inline'` fallback — verify against actual build output before locking `script-src` down), `X-Frame-Options: DENY` (or `frame-ancestors 'none'` in CSP), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and a conservative `Permissions-Policy`.

**#2 — Weak HSTS.** `max-age=63072000` (2 years) is fine, but without `includeSubDomains; preload` the site isn't submitted-preload-eligible and any subdomain (e.g., a future `staging.supakoto.com`) isn't covered. Add both directives once all subdomains are confirmed HTTPS-only.

**#3/#4 — Forms API has no origin check and a toothless rate limiter.** `POST /api/forms` accepts requests from any `Origin` — nothing in `route.ts` reads or validates the `Origin`/`Referer` header. Combined with the in-memory `Map` rate limiter (per warm serverless instance, wiped on cold start, not shared across concurrent instances on Vercel), a scripted attacker can submit at effectively unbounded volume from any page on the internet, burning the Resend send quota and flooding `info@supakoto.com`. The honeypot (`website` field) only stops unsophisticated bots, not a targeted script. Fix: add an `Origin`/`Referer` allow-list check (reject anything not `https://supakoto.com` or the Vercel preview domain) as a cheap first layer, and move rate limiting to a durable store (Vercel KV / Upstash Redis) if this route needs to survive a real abuse attempt — currently in scope-conflict with the "mid-integration, no refactor" instruction only insofar as it touches `app/api/forms/route.ts`, which is explicitly named in the hard constraint; **reported as a defect, not actioned.**

**#5 — Spoofable file-type check.** `ALLOWED_FILE_TYPES.test(value.type)` trusts `File.type`, which the browser derives from the file extension/user agent and which any client (or a hand-crafted multipart request) can set to anything. A `.exe` renamed with a `Content-Type: image/png` header passes the check, gets base64-encoded, and is emailed as an attachment to `info@supakoto.com` — a classic contact-form-to-malware-delivery vector aimed at whoever opens the inbox. Fix: sniff the actual file signature (e.g., the `file-type` npm package reading magic bytes from the buffer) before accepting, independent of the client-declared MIME type.

**#6/#7 — Minor email-field hygiene.** Not exploitable as classic SMTP header injection because the payload goes to Resend's JSON API rather than being concatenated into raw headers, but there's no defensive stripping of `\r\n`/control characters from `subjectName`, and `visitorEmail` used as `reply_to` isn't validated as a well-formed email before being sent. Low severity, cheap to fix: `.replace(/[\r\n]/g, " ")` on `subjectName`, and a simple email regex/`zod` check gating whether `reply_to` is included at all.

**#8 — PII persisted client-side with no TTL.** `logIntent()` in `lib/intent.ts` writes the entire form draft (name, phone, email, plate/vehicle details, free-text message) to `console.info` and to `localStorage` (keyed per intent kind, capped at the last 20 entries, but with no expiry). On a shared or public computer, or in the event of any future XSS on the site, this is PII sitting in the clear indefinitely. Fix: drop the raw `draft` object from what's persisted (keep only non-PII fields like `ref`/`service`/`region` for local debugging), or at minimum gate the `console.info` behind a dev-only flag and add a TTL/expiry sweep to the localStorage writer.

**#9 — Cookies missing `Secure`.** `NEXT_LOCALE` (next-intl's own cookie) and `sk-region` (`RegionProvider.tsx:47`) are set with `Path=/; SameSite=lax` but no `Secure` flag. Low sensitivity (locale/region preference, not auth or PII), but on an HTTPS-only site there's no reason not to set it. `sk-attribution` already conditionally sets `Secure` when `window.location.protocol === "https:"` — the same pattern should be applied to the region cookie, or better, set it server-side via a `Set-Cookie` response header where `Secure` can be unconditional.

**#10/#11 — Dependency advisories.** `pnpm audit --prod --json` reports 0 critical / 4 high / 2 moderate, all against `sharp` and `postcss`/`nanoid` pulled in transitively by `next@15.5.22`. None of these are directly reachable through this app's own runtime input paths today (forms don't feed attacker data into PostCSS's `sourceMappingURL` parsing or into `sharp`'s image pipeline with arbitrary user-supplied images — `next/image` only processes the site's own bundled assets), so real-world exploitability is low, but they're a supply-chain liability that a routine `next` version bump likely resolves. Confirm with a scoped `pnpm update next` + full `pnpm build` before merging.

**#12 — `/dev/kitchen-sink` live in production.** Returns HTTP 200 for both `/dev/kitchen-sink` and `/en/dev/kitchen-sink`. `app/robots.ts` disallows `/dev/` and `/en/dev/` from crawling, but that's advisory for well-behaved crawlers only — it does not prevent direct access, and the page has no `noindex` meta tag as a backstop, no auth gate, and ships as a normal prerendered route in the production bundle. Content itself is low-sensitivity (a UI kitchen-sink page — buttons, cards, a dummy contact-style form with `action="#"` that submits nowhere), so this is reconnaissance/branding exposure rather than a data leak, but it's an unintended production surface. Fix: gate the route behind `process.env.NODE_ENV !== "production"` (return `notFound()` in prod) or exclude it from the build entirely, and add `export const metadata = { robots: { index: false, follow: false } }` as a backstop regardless.

**#13/#14 — Tracking-layer defects, no refactor proposed.** Per the audit's hard constraint, `lib/analytics.ts`/`lib/attribution.ts`/`lib/intent.ts` and the pixel loaders are mid-integration on another branch — findings are reported as defects only. (a) Pixel scripts load from three third-party origins with no CSP to constrain them and no SRI (not feasible for these vendor-controlled, frequently-changing scripts) — this is a direct consequence of finding #1 (no CSP) rather than a defect unique to the tracking code. (b) No PII (email/phone) is passed into `track()` anywhere in the codebase — `EventMap` types and every call site were checked; the Phase 22 "EnrichAM" hashed-phone concern noted in `docs/progress/CONSENT-DECISION.md` appears closed in the current code. (c) `captureAttribution()` runs before any consent mechanism exists, which matches the owner's recorded Option A decision (`docs/progress/CONSENT-DECISION.md`) — stated as fact, no design proposed.

## What is already good (do not touch)

- **No secrets in source or in the built bundle.** Grepped `app/`, `lib/`, `components/`, `content/`, `i18n/`, `scripts/`, `messages/`, `middleware.ts`, `next.config.ts`, and `.next/static/chunks/**` for `re_`, `sk_`, JWT patterns, `AIza`, `supabase.co`, `service_role`. Nothing found. `RESEND_API_KEY` is read via `process.env` only inside the server-only route (`app/api/forms/route.ts`, `runtime = "nodejs"`) and confirmed absent from the compiled `.next/server/app/api/forms/route.js` as a literal value (only `process.env.RESEND_API_KEY` reference, correctly resolved at runtime, never inlined at build time since it's a server route).
- **`.env.example` is honest and correctly scoped.** The four `NEXT_PUBLIC_*` analytics IDs are genuinely public identifiers (see table below); `RESEND_API_KEY` is left blank with a comment that it lives in Vercel only. No overreach.
- **Forms route refuses to fake success.** Missing `RESEND_API_KEY` → 503 with `email_unconfigured`, not a fabricated 200 — avoids silently swallowing leads (`app/api/forms/route.ts:70-74`).
- **Server-side error handling doesn't leak.** Resend failures return a generic `send_failed` to the client; the actual upstream error text is only `console.error`'d server-side (`app/api/forms/route.ts:123-126`).
- **File size/count limits enforced server-side**, not just in the UI (`MAX_FILE_BYTES`, `spec.maxFiles` per form).
- **Field count and length are capped** (`MAX_FIELDS = 24`, `MAX_FIELD_CHARS = 4000`) — bounds a trivial DoS-by-huge-payload vector.
- **Honeypot + `isRef()` format gate** on every submission — cheap, real spam friction.
- **No Supabase anywhere.** Confirmed: no `@supabase` import, no `supabase.co` string, not in `package.json`/`pnpm-lock.yaml`. Owner's belief is correct — fully HELD as documented.
- **i18n routing is a closed set.** `routing.locales = ["ar", "en"]`, `hasLocale()` gate in `i18n/request.ts` with fallback to `defaultLocale`, `localeDetection: false`. No open-redirect or locale-injection surface found; `middleware.ts` matcher correctly excludes `/api`, `/_next`, `/_vercel`, and static files.
- **OG image route (`lib/og.tsx`) has no path traversal risk** — all `fs.readFile` paths are hardcoded constants (font, logo, hero background); `title` is caller-supplied text rendered into the image, never used to construct a filesystem path.
- **No PII sent to ad pixels.** Every `track()` call site was checked; `EventMap` params are IDs/categories/refs only — no raw email or phone in any `fbq`/`ttq`/`gtag` payload.
